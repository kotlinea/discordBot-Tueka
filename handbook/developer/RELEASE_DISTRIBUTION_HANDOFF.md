# 本番専用配布の引き継ぎ指示

記録日: 2026-09-24。状態: 将来作業、実装未着手。現在の開発リポジトリで機能完成を優先し、配布方式の変更は後で扱う。本書は実装済みの仕様でも、公開・リポジトリ作成の実行指示でもない。

## ユーザーの意図と決定状況

- インストールする人は開発しない。リリース配布物は本番の導入・運用に専念できる構成にする。
- 開発向け文書とDev/Stageの起動入口をリリース配布物から除外し、本番だけを起動できるようにする。利用者向けDocsと運用・更新・復旧手順は残す。
- 現在のリポジトリは開発用。開発側のDev/Stage、テスト、開発文書を削除する要求ではない。
- リリース専用リポジトリへの分離案はあるが、現時点で二つのリポジトリを管理する負担に懸念がある。**2リポジトリ化は未決定であり、先行して実施しない。**
- **当面は機能完成を優先する。** 本書の配布整備を機能開発の新しい前提条件にしない。「機能完成」が既存機能の完成度改善までか、新機能群も含むか、対象版と範囲は再開時に確認する。
- この優先順位は配布整備との比較であり、未検証の機能や実Stage受入を完了扱いにするものではない。既存のT1/C1/P3-G等の証拠・受入状態は維持する。全体の着手順を変更する際は[実行計画](EXECUTION_PLAN.md)と[ROADMAP](../../ROADMAP.md)へ具体的に反映する。

参考にしたのは[MisskeyのDocker導入手順](https://misskey-hub.net/ja/docs/for-admin/install/guides/docker/)の「取得→設定→準備→起動」という分かりやすい流れ。コマンドや内部構成をそのまま移植する意図ではない。

## 再開時に決める事項

本番専用の配布物と、リポジトリを二つにすることは別の判断として扱う。

| 選択肢 | 判断材料 |
| --- | --- |
| 同じリポジトリから本番専用Releaseアーカイブを生成 | 管理先を増やさず配布内容を分離できる。取得・更新手順、ソースとの版対応を定義する |
| 別のリリースリポジトリへ配布物を生成・同期 | インストール用の入口を分離できる。同期、権限、公開失敗、版ずれへの対応が必要 |

選定前に、対象利用者、サポートOS/CPU、配布先、版番号、Imageの公開方法、更新経路、保守負担を比較する。別リポジトリへ同じソースを手作業で二重管理しない。どちらでも開発側を正本にして、明示した対象ファイルから配布物を再生成できる形を基本案とする。

検証済みのビルド済みImageを取得して起動する方式を推奨案とする。利用者側ビルドの要否、Registry、署名・検証方法は未決定。前の会話で提示した短縮コマンドやラッパーも提案段階であり、採用済みと扱わない。

## 実施順序と完了条件

ユーザーが配布整備の再開を指示した時点で、次の順序を具体的な実行計画へ展開する。

1. **現状と対象版を確認する。** AGENTS.mdから指示を読み、機能の完成範囲、未受入事項、設定・運用入口を棚卸しする。配布方式と対象環境の決定を記録する。
2. **配布契約を定義する。** 含めるファイル、除外する開発資産、Image/版/digest、設定・データ保存先、更新・復旧、ライセンス等の同梱物を明記する。開発側とインストール側の責任を分ける。
3. **本番専用配布物を生成する。** 明示したファイル一覧から生成し、Dev/Stageの起動入口・開発文書・実秘密値が混入しないことを検査する。本番に必要な実装、Migration、運用機能を巻き込んで削除しない。
4. **初回導入を一本化する。** 取得→設定生成→必須値入力→Image準備→起動→HTTPS/ログイン/Bot応答確認を、一つの導入手順で辿れるようにする。必須入力・自動生成・任意機能の設定を分ける。環境名の選択を利用者へ要求しない。
5. **更新・復旧を受け入れる。** 既存設定・鍵・データを保持し、更新失敗から再開できることを確認する。DB互換性を確認せず古いImageへ戻す手順を作らない。復旧時の外部副作用照合と明示解放を維持する。
6. **配布物だけでクリーン導入する。** 開発リポジトリ、Host Python/Node、開発用成果物がない対象Hostで確認する。成功URL、サービス状態、再試行方法を表示し、内部health成功と外部公開・OAuth成功を区別する。
7. **公開手順を確定する。** CI・Stageの受入証拠と配布物を対象Commit/版/digestで対応付ける。配布方式を決めた後に生成・公開を自動化し、現行ガイドを更新する。新リポジトリの作成・外部公開・実Host操作は、その時点の明示依頼の範囲で実施する。

最終受入では、本番専用の起動、日英利用者Docs、運用手順、開発資料の非同梱、初回導入、再実行、更新、Backup/Restore、認可・秘密値・データ保持を配布物に対して検証する。ローカル、独立Linux Host、Remote CI、実Stageの証拠は分けて残す。
